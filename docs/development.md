# blocks.system development system

This repository deliberately uses the same documentation and release shape as
`p5.waves`, without coupling either library to the other.

## topology

- `blocks.system.mjs` is the canonical ESM source.
- `blocks.system.min.mjs` is generated by `npm run build:min`.
- `blocks.system.css` contains only the reusable field and block styles.
- `index.html` is the interactive showcase.
- `docs/` contains shared site styling, guide, API, examples index and about.
- `examples/<name>/` contains complete standalone examples.
- `docs/blocks.system.manifest.json` is generated by `npm run manifest`.
- `tests/` checks the API contract, source/min parity, docs and local links.

## documentation contract

When public behaviour changes, update these layers in one commit:

1. `README.md`
2. `README_NL.md`
3. `docs/guide.html`
4. `docs/api.html`
5. relevant standalone examples
6. contract tests and generated manifest

The manifest derives version from `package.json`, API keys from the real ESM
export, and example names from the filesystem. Its committed copy says
`unreleased`, because a Git commit cannot contain its own final hash. GitHub
Pages replaces that field with the deployed commit so the live manifest cannot
lag behind the published source.

## local verification

```powershell
npm install
npm run check
```

Then open `http://localhost/blocks.system/` and check the showcase plus all
three standalone examples at desktop and narrow widths.

## publication

1. Work on a branch, never directly on `main`.
2. Run `npm run check` and `git diff --check`.
3. Stage only intended public files. Local `AGENTS.md` stays untracked.
4. Push the branch and review the GitHub Actions test.
5. Merge to `main` only after review; the Pages workflow deploys from `main`.
6. Verify the live showcase, examples, API and manifest routes.
7. Create a version tag only when the public API is ready to pin from jsDelivr.
